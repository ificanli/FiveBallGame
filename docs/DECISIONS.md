# 《五球满贯》Steam 版本决策日志

## 2026-08-17：采用轻量规格驱动研发工作流

### 决策

- 使用 OpenSpec 管理重要功能变更的提案、规格、技术设计、任务与归档；
- 使用项目自定义 `STEAM_PRODUCT_WORKFLOW.md` 管理里程碑、排期、审核、真人试玩和发布门；
- `PROJECT_STATUS.md` 作为跨窗口唯一进度源；
- 借用 BMGD 的游戏文档与 QA 模板思想，但不安装完整 Agent 组织；
- 暂不安装 GSD、Spec Kit、Game Studios 全套，避免多套规格系统和 AI 官僚化；
- 正式 Godot 仓库创建后再执行 `openspec init`。

### 原因

- 当前项目周期已从三日 HTML Demo 升级为 6～9 周 MVP 与长期 Steam 产品；
- 仅靠聊天记忆会在任务累积后丢失状态、重复开发或错误宣称完成；
- OpenSpec 足够轻量，可将每次重要变更固定为可审查的持久化档案；
- 游戏是否好玩仍必须由真人验收，不能交给规格框架或自动测试代判。

---


## 2026-08-17：最终目标改为 Steam 独立游戏

### 决策

- 《五球满贯》不再以比赛评审偏好作为主要设计约束；
- itch.io 等网页平台作为公开 Alpha 与社区入口；
- Steam 作为正式商业版本目标；
- 比赛与节展仅作为可选曝光渠道。

### 原因

- 台球物理、功能墙和徽章 Build 需要逐渐理解；
- 真正价值来自长局构筑、残局经营和技巧成长；
- 产品的独游属性强于短平快比赛属性；
- 网页试玩适合降低门槛，Steam 更适合承载完整内容和长期口碑。

### 当前优先级

1. 徽章流派重构；
2. 章节球桌差异；
3. 完整 Run 与时长验证；
4. itch.io Alpha；
5. Steam 商店页与 Demo。

### 证据边界

这是产品方向决策，不代表当前版本已经达到 Steam 商业发布标准。所有长局内容量、单局时长和市场表现仍需外部试玩验证。

---

## 2026-08-17：正式引擎确定为 Godot 4.x

### 决策

- Steam 正式版使用 **Godot 4.x**；
- 新建独立 Godot 工程，不在比赛版 HTML 单文件上继续叠补丁；
- 比赛 HTML 版冻结并作为规则、手感和网页 Alpha 参照；
- 核心球体物理采用固定时间步长的自定义 2D 圆形碰撞；
- 预测辅助线与实际模拟必须调用同一套物理规则；
- 所有随机球桌和奖励使用可复现 Seed；
- 首发目标平台为 Windows，开发时兼顾 Linux 与 Steam Deck；
- Steamworks、手柄、云存档和成就在纵切稳定后接入。

### Godot 负责

- 2D / 2.5D 渲染；
- UI、动画、粒子、Shader 与音频；
- 输入、窗口和平台导出；
- 场景、资源和内容数据管理。

### 自定义规则层负责

- 母球与数字球碰撞；
- 库边及功能墙反射；
- 摩擦、低速收尾与回合结束；
- 预测轨迹；
- 球体状态、组合识别和计分；
- 固定种子回放与规则测试。

### 第一技术里程碑

先制作一张纯技术球桌，只包含：

- 五档力度；
- 母球与 6 颗数字球；
- 标准库边反弹；
- 复制墙、染色墙；
- 简洁 / 标准 / 完整辅助线；
- 固定 Seed 重放；
- 与网页比赛版的手感对照。

该里程碑未通过前，不制作正式章节和大规模徽章内容。

## 2026-08-17：美术基线与 PvP 验证进入核心立项

### 美术决策

- 继续保留台球、圆球、数字、颜色、库边反弹和母球等基础视觉语法；
- 正式版采用**风格化台球**，不照搬当前网页比赛版的场景与 UI；
- 具体风格仍处于探索期，机械竞技、神秘仪式、俱乐部潮流、玩具工坊等均可制作视觉提案比较；
- 暂不把数字球替换成玩偶或不规则角色，避免损害碰撞半径、数字颜色和球路预测的可读性；
- 场景风格与 UI 风格必须作为 Godot 正式纵切的一部分重新设计。

### PvP 决策

- Steam 产品立项阶段增加一个 PvP 核心验证；
- PvP 的目标不是复制传统八球，而是验证《五球满贯》的做球、组合、残局与风险决策能否形成长期玩家对抗；
- 第一验证方向为：**双方轮流使用同一张持续变化的物理球桌**；
- 首个 PvP 黑盒不加入联网、排位和大规模徽章池，先用本地轮流 / AI 验证直接对抗是否成立；
- 异步同种子竞分可作为低成本补充模式；
- “双方各玩独立球桌并互扔干扰”暂不优先，避免退化成常见的垃圾行对战结构。

### 证据边界

PvP 目前是需要验证的产品假设，不代表已经确认进入 Steam 1.0。只有对抗规则能产生读局、做球、走位、防守和风险决策，且等待时间可接受时，才进入正式产品范围。

## 2026-08-17：核心身份锁定为碰撞构筑，否决落袋满贯

### 问题

当前单机与共享球桌 PvP 都以“碰撞即收集”为基础，与传统台球的落袋、连杆、走位、犯规和安全球差异较大。若完全放弃这些语法，容易让台球用户产生违和，也浪费圆桌、球杆和六袋结构天然具备的用户基础。

### 最终决策

正式产品不得改变已经获得认可的核心循环：

```text
发射母球
→ 撞到哪些彩色数字球，就收集哪些球
→ 激活球撞功能墙后被加工
→ 一杆结束后立即结算，或保留球组继续做大组合
→ 第六球爆仓
```

否决“数字球必须落袋后才进入组合”的落袋满贯方案。原因：

- 它替换了核心玩法，而不是扩展核心；
- 一杆多撞收集是当前最具辨识度、也已获得作者认可的体验；
- 落袋收集会降低连撞密度，并让功能墙、残局经营和五球槽围绕另一套目标重新设计；
- 为争取传统台球用户而改写核心，会同时损害现有产品身份。

正式定位优先使用“物理碰撞做牌 / 碰撞构筑游戏”，而不是承诺传统八球或斯诺克规则。视觉仍可保留球杆、圆球、库边与台面等台球触感，但场景和 UI 不应让玩家误以为必须遵守传统落袋规则。

### 传统台球语法的可用边界

可借用，但不能替换核心：

- 球杆蓄力与精细瞄准；
- 库边反弹与走位；
- 可选的旋转、回旋与侧旋；
- 安全球和封路思维；
- 球袋作为清台、废球回收、特殊奖励或个别章节机关；
- 台球材质、碰撞声与击球仪式。

不可作为基础规则：

- 落袋才算收集；
- 传统八球分组与黑八胜负；
- 报袋作为默认要求；
- 进球续杆替换现有每杆结算 / 保留决策；
- 因落袋规则删除五球槽、爆仓与功能墙做球。

### PvP 影响

PvP 必须从“碰撞即收集”的核心出发重新设计。共享球桌抢球、公共目标争夺、残局改写和异步同种子均可继续验证；落袋满贯不再进入开发路线。
