# 《五球满贯》开发准备与工具链评估 v0.1

更新时间：2026-08-17
目标：Godot Steam MVP 开工前准备

> 原则：插件越少越好。核心物理、规则和存档必须由项目自己掌控；AI 工具只能提高编辑、运行和检查效率。

---

# 一、结论

## 正式采用

1. **Godot 4.7.1 Stable**：锁定具体引擎版本。
2. **Git + Git LFS**：源码与二进制资产管理。
3. **GdUnit4 6.2.x**：单元、场景和 CI 测试。
4. **项目自研 Golden Replay**：固定 Seed、输入日志、碰撞事件和最终 Hash。
5. **GitHub Actions + godot-ci**：无头验证、Windows/Linux 导出、Artifact。
6. **GodotSteam 4.20.x**：单机纵切稳定后再接 Steam。
7. **Steam MultiplayerPeer / Networking Sockets**：本地 PvP 和 ENet 原型通过后再接。
8. **Godot 内置 Resource、输入映射、本地化和版本化 JSON 存档**。

## 隔离试用

1. **Godot AI（hi-godot/godot-ai）MCP**：首选 Godot MCP 试验项。
2. **GoPeak Godot MCP**：如果 Godot AI 工具过多或不稳，作为保守备选。
3. **godot-gdscript-toolkit**：验证兼容后用于 `gdformat/gdlint`。
4. **Claude-Code-Game-Studios / UltraGameStudio**：只借鉴模板和质量门，不整体接管项目。

## 暂不采用

- 同时安装多个 Godot MCP；
- MCP 任意 `execute_code` 全权限模式；
- GUT 与 GdUnit4 同时存在；
- 第三方存档插件；
- 默认刚体承担核心球体物理；
- 开工早期接 Steam、云存档、联网和排行榜；
- 49 Agent / 70 Skill 级“AI 工作室”直接进入正式工程。

本机现状：Git、Python、Node.js 已安装；Godot 尚未加入 PATH；`E:\NewGame-steam` 尚未创建。

# 三、Godot MCP

## 首选试验：Godot AI

项目：https://github.com/hi-godot/godot-ai

公开状态：MIT、约 1700+ stars、近期活跃；支持 Godot 4.5+，具备场景/脚本/资源编辑、运行、日志、截图、测试和运行时检查。

### 对本项目最有帮助

- AI 可启动和停止项目；
- 读取真实 Godot 错误和远程场景树；
- 截图检查球桌与 UI；
- 运行测试；
- 在编辑器状态中检查场景，不靠猜 `.tscn`；
- 后期辅助调整 Theme、动画、粒子和资源。

### 风险

- 生态仍新；
- 工具过多会污染上下文；
- 场景自动编辑的 diff 比脚本更难审；
- 高权限执行可能直接破坏工程；
- 复杂 UI、美术合成和游戏设计仍不能交给 MCP 自动决定。

### 使用边界

- 只在 `experiment/godot-mcp` 分支试装；
- 初期只开放：读取、运行、日志、截图、测试；
- 通过一周试验后才开放场景写入；
- 禁用任意代码执行；
- 每次大改前提交 Git；
- 插件必须 Editor-only，不进入导出包；
- MCP 出问题时，删除 Addon 不影响规则层。

## 备选：GoPeak

项目：https://github.com/HaD0Yun/Gopeak-godot-mcp

优点：MIT、活跃、默认 compact profile；LSP、DAP、运行时和测试按能力组启用，风险边界写得较清楚。

若 Godot AI 出现工具噪音、兼容或稳定性问题，退回 GoPeak compact。不要并装。

## 不优先的同类

- `tomyud1/godot-mcp`：功能清晰，但活跃度和运行时能力不占优。
- Funplay 等 100+ 工具方案：功能强，但高权限面和审计成本过高。

# 五、测试体系

## GdUnit4

项目：https://github.com/godot-gdunit-labs/gdUnit4

选择原因：Godot 4 专用、支持 GDScript/C#、Mock、参数测试、场景测试和 GitHub Actions，兼容矩阵清楚。

测试：

- 圆—圆、圆—库边碰撞；
- 固定输入一致性；
- 功能墙；
- 牌型；
- 三态、爆仓和补球；
- 徽章顺序；
- PvP 抢球、释放和回合公平。

GUT 同样成熟，但不要双框架并存。

## Golden Replay（必须自研）

输入：

```text
physics_version + content_version + seed
+ initial_snapshot + shot_input
```

输出：

```text
collision/wall/collection events
+ final_ball_states + state_hash + ticks
```

建立 10～20 个固定球路：直撞、擦碰、连撞、撞库、多球拥挤、功能墙、低速残局和高速穿模风险。

通过标准：相同版本、初态和输入重复运行结果一致；预测与实际使用同一个模拟器。

- GdUnit4；

- 缺失资源检查；

- 发布 Artifact；
- 启动包冒烟；

# 七、Steam 与 PvP

GodotSteam：https://godotsteam.com/

采用顺序：

```text
本地热座 PvP
→ 简单 AI
→ 回放与 Hash
→ LocalTransport
→ ENet 双进程与断线测试
→ 真人网络验证
→ Steam Lobby + P2P Relay
```

Steam 层只负责连接、邀请和传输。物理采用房主权威：输入同步、房主模拟、杆后快照校验，不使用 `MultiplayerSynchronizer` 每帧同步球体。

PvP 核心没通过之前，不安装 GodotSteam 到主工程。

# 八、存档、本地化与数据

## 存档

不用第三方插件。采用版本化 JSON 或 Godot Resource：

- `save_version`；
- 临时文件原子写入后替换；
- 明确迁移函数；
- Debug 导出/导入；
- Run 存档与元进度分离。

## 本地化

使用 Godot 内置翻译资源；首发中文简体 + 英文；脚本不散落长文案；测试文本溢出和缺失 key。

## 内容数据

使用自定义 Resource：

- `BadgeData`；
- `ItemData`；
- `TableData`；
- `DealerData`；
- `ScoringData`。

MVP 不开发独立内容编辑器，先利用 Inspector 与校验脚本。

## Analytics

MVP 先写本地 JSON，可一键导出。公开 Alpha 再考虑匿名上传、Talo 或 Steam Stats。数据平台不能侵入物理与规则层。

# 十、推荐工作流

## 分支

```text
main              可发布
integration       日常集成
feature/*         功能
experiment/*      MCP、物理、PvP、美术实验
release/*         发布候选
```

## 每个功能的 Definition of Done

```text
设计/ADR 已更新
→ 规则测试
→ Golden Replay（若涉及物理）
→ 真实启动与截图
→ 人工试玩说明
→ 文档与交接
→ Reviewer 验收
```

## 提交策略

- 小提交；
- 生成场景和二进制资产用 Git LFS；
- `.godot/`、导出目录和本地 MCP token 不入库；
- `addons/` 明确区分 vendored 与本地试验插件；
- 第三方插件记录版本、commit、许可证和移除方法。
