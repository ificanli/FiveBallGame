# 《五球满贯》Steam 立项评估：引擎、美术与内容规模 v0.1

更新时间：2026-08-17

> 本文用于重新评估《五球满贯》的正式 Steam 立项。比赛版只作为核心验证与历史原型，不默认继承其 HTML 工程、美术包装和内容规模。

---

# 一、先给结论

## 已确认立项方案

- **引擎：Godot 4.x（已确认）**
- **物理：自研固定步长 2D 圆形碰撞，不把核心手感完全交给通用刚体引擎**
- **画面：台球 + 风格化表现；保留圆球、颜色、数字与库边反弹直觉**
- **包装：具体场景风格与 UI 风格待视觉探索，明确不沿用当前网页版；不把球直接替换成玩偶或不规则角色**
- **核心对象：将传统台球升级为“彩色数字核心 / 竞技球体”，允许不同章节改变材质和局部外观**
- **内容目标：单次成功 Run 45～70 分钟；首次成功通关约 6～12 小时；完整掌握 20 小时以上**
- **首发 1.0 建议：5 个章节、15～18 张有效球桌、70～90 枚高质量徽章、20～30 种道具、6 名庄家、6～8 种功能机关、4 套初始构筑**

这不是最终冻结值。正式制作前先完成一个 30～45 分钟的 Steam 纵切，验证引擎手感、视觉包装和三套徽章流派。

---

# 二、引擎怎么选

## 方案 A：Godot 4.x —— 推荐

### 适合本项目的原因

- 2D 渲染、动画、粒子、Shader、UI 和音频能力完整；
- 导出 Windows、Linux，后续适配 Steam Deck 较自然；
- 无运行时抽成，适合独立开发；
- 场景与资源结构适合拆分球桌、庄家、徽章、机关和章节；
- GDScript 迭代快，便于制作大量规则内容；
- 可接 Steamworks 插件，实现成就、云存档、统计等；
- 比 Electron 网页壳更像正式桌面产品，包体、输入和全屏管理更干净。

### 必须注意

《五球满贯》的核心是可重复、可记忆的球路。不能直接把所有球交给默认刚体，然后祈祷不同帧率下结果一致。

推荐：

```text
固定时间步长
+ 自定义圆形碰撞
+ 自定义库边反射
+ 自定义摩擦与低速收尾
+ 预测和实际共用同一规则
+ Seed 化球桌生成
```

Godot 主要负责：

- 渲染；
- UI；
- 动画与特效；
- 音频；
- 输入；
- 场景和资源管理；
- 平台导出。

核心物理与组合规则仍应保持可测试、确定性的独立模块。

### 成本

- 需要从比赛版 HTML/JS 重写工程；
- 旧版逻辑可作为规格和算法参考，但不建议逐行移植；
- 需要重新建立规则测试、回放测试和种子测试。

---

## 方案 B：TypeScript + Phaser/Pixi + Electron/Tauri

### 优点

- 复用比赛版 JavaScript 思路最快；
- 网页 Alpha 和桌面版更容易共享代码；
- 自定义物理、测试和埋点方便；
- itch.io HTML5 发布成本低。

### 缺点

- Electron 包体和运行开销偏大；
- 手柄、Steam Deck、全屏、窗口和 Steamworks 集成需要额外工程；
- UI、粒子、Shader、动画和资产工作流不如专用引擎统一；
- 长期维护容易继续堆成比赛版单文件补丁。

### 适用条件

如果目标是 3～6 个月内快速做出网页与 Steam 双版本，并且团队最熟悉 TypeScript，可以选此方案。

但正式独游目标下，建议不要直接套壳比赛版，而应至少重构为：

```text
TypeScript
+ 模块化规则层
+ Phaser/Pixi 表现层
+ 自动测试
+ Electron/Tauri 桌面壳
```

---

## 方案 C：Unity

### 优点

- 2D/3D、Steamworks、资产商店和团队招聘生态成熟；
- 做 2.5D 球桌、灯光与高级后处理方便；
- 大规模产品化能力强。

### 缺点

- 对当前规模偏重；
- 工程与构建复杂度高于 Godot；
- 迭代规则型 2D 游戏未必更快；
- 授权与长期平台政策需要持续关注。

### 判断

除非团队已有成熟 Unity 工作流或计划全面 3D 化，否则不作为首选。

---

## 引擎最终建议

### 正式 Steam 产品

> **Godot 4.x + 自定义固定步长 2D 物理。**

### 网页 Alpha

短期继续维护现有 HTML 版，用于 itch.io 测试。不要立刻要求 Godot Web 与桌面版本完全同步。

### 迁移策略

```text
比赛 HTML 版冻结
→ Godot 技术验证
→ 重建基础击球、预测与功能墙
→ 对照固定种子验证结果
→ 重建徽章和 Run
→ 形成 Steam 纵切
```

# 三、是否还应该用“台球”包装

## 推荐：保留台球物理语法，不必保留传统台球美术

必须保护的视觉信息：

- 圆球；
- 明确颜色；
- 清楚数字；
- 球体碰撞；
- 库边反弹；
- 白色或中性母球；
- 球桌边界；
- 力度和球路预测。

这些不是临时包装，而是玩家理解物理结果的基础语言。

如果全部换成玩偶、怪兽或不规则物体，会产生问题：

- 碰撞半径与画面不一致；
- 数字和颜色可读性下降；
- 玩家难以预测反弹；
- 一杆多撞变得混乱；
- 角色美术量激增；
- 核心容易被误解成弹珠战斗或玩具碰撞。

## 不建议：直接把每颗球换成完整玩偶

原因：

- 玩偶形状不适合精确碰撞；
- 角色朝向、动画和表情会抢占数字信息；
- 五颗球槽和组合计算需要快速识别；
- 玩家会期待玩偶拥有独立能力，系统复杂度失控。

玩偶更适合：

- 庄家；
- 桌边观众；
- 徽章形象；
- 球桌机关；
- 解锁收藏；
- 球体的轻量皮肤，而不是替换物理本体。

# 四、推荐美术方向

## 方向 A：机械竞技球桌 —— 首选

### 核心气质

- 精密；
- 危险；
- 华丽；
- 舞台化；
- 像一台可以被构筑和作弊的物理机器。

### 视觉对象

- 数字球：高饱和珐琅、玻璃或能量核心；
- 母球：中性白色核心，状态以尾迹表达；
- 功能墙：机械机关，有明确入口、充能和方向；
- 徽章：安装在桌边的实体机械徽记；
- 庄家：拥有自己球桌规则的对手或经营者；
- 章节：不同材质、机关和舞台灯光。

### 优势

- 保留台球可读性；
- 允许做很强的机关动画；
- 徽章安装与功能墙加工都符合世界逻辑；
- 能与普通酒吧台球区分；
- Steam 截图有稳定产品身份。

---

## 方向 B：神秘赌场 / 奥术球桌

### 视觉

- 黄铜、深色木、丝绒、烛光；
- 数字球像占卜宝珠；
- 功能墙是魔法镜、染色坩埚、复制法阵；
- 徽章是护符和契约。

### 优势

- 与 Roguelite、庄家和高倍率较契合；
- 氛围强；
- 容易塑造章节和 Boss。

### 风险

- 太接近扑克、赌场与《Balatro》的联想；
- 深色画面容易降低球体可读性；
- “赌博”会压过物理做球的独特身份。

建议只吸收材质与仪式感，不把产品完全包装成赌场。

---

## 方向 C：玩具工坊 / 迷你竞技场

### 视觉

- 木制轨道；
- 发条机关；
- 玻璃弹珠；
- 桌边玩偶观众；
- 每张桌子像一个玩具关卡。

### 优势

- 亲和、适合泛用户；
- 可以把球桌机关做得夸张；
- 收藏和皮肤自然。

### 风险

- 可能显得过于儿童化；
- 高倍率、庄家和长局构筑的压迫感会减弱；
- 若球体过于透明，颜色数字识别困难。

可作为章节主题，不建议作为唯一主风格。

---

## 推荐混合方向

> **当前只冻结“台球 + 风格化”基线；机械竞技、奥术仪式、俱乐部潮流、玩具工坊等均作为视觉提案探索，不提前锁定最终比例。**

视觉探索时必须同时比较场景、球体、功能墙、徽章、庄家和 UI，而不是只换背景皮肤。评价标准包括：球路可读性、数字颜色识别、Steam 截图辨识度、动画成本和长期章节扩展能力。

---

# 五、球体应该怎么设计

## 基础数字球

必须满足：

- 颜色差异足够大；
- 数字在高速运动、缩小和球槽中仍可读；
- 色盲模式能通过纹理与符号区分；
- 收集、本手、废球三态明显；
- 不同材质不改变碰撞认知。

建议外观结构：

```text
外圈：颜色 / 花纹
中心：高对比数字
边缘：状态光环
尾迹：激活来源与功能墙归属
```

## 球体人格化边界

可加入：

- 微弱表情；
- 球体外壳纹章；
- 被加工时短暂动画；
- 稀有球皮肤；
- 庄家专属球。

不建议加入：

- 完整四肢；
- 改变碰撞轮廓的角色造型；
- 每颗球独立复杂技能；
- 遮挡数字的脸部设计。

## 可替换主题

后续可做皮肤，但保持统一碰撞体：

- 经典竞技球；
- 玻璃弹珠；
- 机械齿轮球；
- 奥术宝珠；
- 发条玩具球；
- 星体球。

皮肤是表现层，不改变核心规则。

# 六、正式产品内容规模估算

## 1. Steam 纵切 / 首个公开 Demo

目标：20～40 分钟，能形成至少一次清晰 Build。

建议内容：

- 2～3 个章节；
- 6～9 张有效球桌；
- 3 名庄家；
- 24～36 枚徽章；
- 8～12 种道具；
- 4 种功能墙 / 机关；
- 3 套初始构筑方向；
- 1 个教程；
- 1 个挑战模式或每日种子入口；
- 中英文；
- 基础成就和统计可暂不开放。

### Demo 的三套必成型流派

1. 纯色 / 染色流；
2. 重复数字 / 复制 / 炸弹流；
3. 撞库 / 连锁碰撞技术流。

如果三套打法录像看起来仍然差不多，不能继续堆内容。

---

## 2. Steam 1.0 最小商业版

目标：45～70 分钟单次成功 Run；首次成功通关约 6～12 小时。

建议内容：

### 章节与球桌

- 5 个章节；
- 每章 3 张常规桌 + 1 张庄家桌；
- 单局随机经历其中 12～16 桌；
- 总计 15～18 张真正具有机制差异的球桌模板；
- 每章至少一种专属机关与桌面问题。

### 庄家

- 6 名庄家；
- 每名有专属球桌、规则和表现；
- 不能只是目标分更高；
- 至少迫使 2～3 类 Build 改变打法。

### 徽章

- 70～90 枚；
- 其中至少 40 枚会改变击球目标、球路或风险；
- 纯数值放大徽章控制在总量的 25% 以内；
- 8 个主要流派；
- 10～15 枚跨流派桥梁；
- 5～10 枚高风险成长核心。

### 道具

- 20～30 种；
- 容错、改球、挪球、清台、重充能、一次性规则修改；
- 不用大量道具替代球路技巧。

### 功能机关

- 6～8 类；
- 复制、染色为基础；
- 后续机关必须改变物理路径或球体价值；
- 避免堆成需要查百科的机关表。

### 初始构筑

- 4 套起始球杆 / 角色 / 套件；
- 改变开局资源和玩法偏好；
- 不建议首发做十几个角色。

### 模式

必做：

- 标准 Run；
- 教程；
- 每日 / 固定种子挑战；
- 图鉴与统计；
- 成就。

可延后：

- 无尽模式；
- 自定义挑战；
- PvP；
- 创意工坊。

---

## 3. 理想扩展版

若 1.0 市场验证良好，再扩展：

- 100～140 枚徽章；
- 8～10 名庄家；
- 25～30 张机制桌；
- 8 套初始构筑；
- 无尽挑战；
- 周常种子；
- 模组或球桌编辑器；
- 多平台；
- PvP 先做共享球桌核心黑盒；联网、排位和完整徽章对战另行验证。

不要在首发前承诺此规模。

# 七、内容量不是越多越好

## 一个“有效球桌”的标准

必须至少改变一项：

- 瞄准方法；
- 力度选择；
- 撞库价值；
- 功能墙使用方式；
- 废球管理；
- 球槽风险；
- 组合价值；
- 球桌动态。

只改变障碍位置、球数量或目标分，不算新内容。

## 一个“有效徽章”的标准

至少改变一项：

- 玩家优先撞什么球；
- 是否主动使用功能墙；
- 选择什么力度；
- 是否追求撞库或间接碰撞；
- 是否接受污染球；
- 何时结算或继续；
- 如何管理废球和桌面。

只有 `+10 分`、`+2 倍率` 的徽章主要用于节奏校准，不应成为内容主体。

# 八、开发周期粗估

以下以 1 名主开发 + AI 辅助 + 少量外包美术/音频为假设。

## 纵切 Demo

约 2～4 个月：

- Godot 技术验证与重写：2～4 周；
- 核心物理、预测、规则和测试：2～4 周；
- 3 套流派与 2～3 章节：3～6 周；
- 正式表现、教程、音频与打包：3～5 周；
- 外部试玩与迭代：持续进行。

## 1.0

约 9～18 个月：

- 取决于美术目标、内容质量、外包投入和外部测试；
- 若坚持高质量 70～90 枚徽章与 15～18 张机制桌，内容设计和测试会成为主要成本，而非基础代码。

这是粗估，不是排期承诺。

# 九、立项前必须完成的三个验证

## 验证 1：Godot 手感复现

做一个纯技术房间：

- 五档力度；
- 母球与 6 颗数字球；
- 侧墙反弹；
- 复制墙、染色墙；
- 标准辅助线；
- 固定种子回放。

目标：手感不低于网页比赛版。

## 验证 2：三套流派录像可辨识

分别录制：

- 染色纯色流；
- 复制炸弹流；
- 撞库连锁流。

不看 UI，只看击球录像，也应能分辨打法差异。

## 验证 3：30 分钟 Run 不重复

制作 3 章 9 桌纵切，真人试玩验证：

- 每章是否改变球路问题；
- 20 分钟后是否仍有新决策；
- 徽章是否改变击球，而非只提高分数；
- 失败是否促使再开一局。

三个验证全部通过，再冻结 1.0 内容规模。

# 十、当前决策状态

## 已确认

1. 采用 Godot 4.x 作为正式 Steam 引擎；
2. 核心物理使用固定步长自定义 2D 碰撞；
3. 比赛 HTML 版冻结，Godot 新工程独立开发。

## 待确认

1. 是否确认“保留圆球与数字，只升级为机械竞技球体”；
2. 是否以“机械竞技 + 奥术仪式 + 少量玩具人格”为主风格；
3. Steam Demo 是否先按 3 章、9 桌、30 枚左右徽章制作；
4. 1.0 是否先按 5 章、15～18 张机制桌、70～90 枚徽章估算；
5. 是否将单次成功 Run 初步目标调整为 45～70 分钟。

下一步先制作 Godot 技术纵切；不要先画 90 枚徽章和 18 张桌子的饼。
