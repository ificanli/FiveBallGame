# 《五球满贯》插件与工作流选型 v0.1

更新时间：2026-08-17
状态：已选型，待正式 Godot 仓库初始化

## 结论

采用“轻量规格流 + 游戏制作门禁 + Godot 执行桥”，不安装大型多 Agent 工作室。

### 正式采用

1. **OpenSpec**：管理每项功能变更的提案、需求、技术设计、任务与归档。
2. **项目自定义 Steam 游戏研发工作流**：管理里程碑、排期、评审、真人试玩和发布门禁。
3. **BMGD 的部分模板思想**：借用 Game Brief、GDD、Architecture、Sprint、Playtest、Retrospective 结构，不安装整套 Agent 系统。
4. **GdUnit4 + Golden Replay + CI**：作为实现验收的机器证据。
5. **Godot MCP**：基础工程和 CI 稳定后，仅在隔离分支试装一套。

### 暂不采用

- Claude-Code-Game-Studios 全套 49 Agent / 70+ Skills；
- BMGD 全模块直接接管项目；
- GSD Core 与 OpenSpec 同时安装；
- Spec Kit 与 OpenSpec 同时存在；
- 自动跳过人工批准的全自动 Apply；
- 多套 Godot MCP 并装。

## 为什么选择 OpenSpec

- 轻量，适合个人或小团队；
- 规格均为 Markdown，可被 PiAgent 和其他窗口读取；
- 每个变更独立保存：proposal、specs、design、tasks；
- 支持先探索，再提案，再实现，再验证，再归档；
- 能解决聊天上下文膨胀后状态丢失的问题；
- 不强迫我们使用大型角色组织。

## 为什么不直接采用 BMGD 全套

BMGD 的阶段划分适合游戏项目，但全套工作流对当前个人 Steam MVP 偏重，而且其 Godot 指南仍以 Godot 4.2+ 与 GUT 为示例，与我们锁定的 Godot 4.7.1 + GdUnit4 不完全一致。

采用其思想：

- Game Brief；
- GDD；
- 技术架构；
- Sprint / Story；
- QA 计划；
- Playtest；
- Retrospective。

不采用其完整 Agent 组织与命令体系。

## 为什么暂不采用 GSD Core

GSD 的 Discuss → Plan → Execute → Verify → Ship 循环很好，但它依赖干净上下文子 Agent 执行。当前 PiAgent 子 Agent 写入能力不稳定，直接安装无法发挥主要优势；同时与 OpenSpec 的规格档案重复。

我们会吸收它的五步循环，但不同时安装第二套规格系统。

## OpenSpec 在本项目中的职责边界

OpenSpec 管：

- 为什么做这个变更；
- 玩家需求和验收场景；
- 技术方案；
- 任务拆分；
- 变更验证和归档。

OpenSpec 不管：

- 产品总路线；
- 里程碑优先级；
- 真人试玩结论；
- 是否好玩；
- 版本发布决策。

这些由项目工作流和人类产品负责人决定。

## 正式仓库初始化方式

正式工程目录创建后执行：

```bash
cd E:/NewGame-steam/FiveBallGrandSlam
openspec init
openspec config set telemetry.enabled false
```

随后将本目录中的权威决策与计划复制/链接到正式仓库的 `docs/`。

## 使用规则

### 必须创建 OpenSpec Change

- 新系统；
- 重要玩法修改；
- 物理规则修改；
- 存档结构修改；
- PvP 协议修改；
- 跨多个模块的重构；
- 影响 Golden Replay 的改动。

### 可以直接改

- 明确的小 Bug；
- 文案和错别字；
- 不改行为的纯重构；
- 已有规格覆盖的微小表现修正。

### 人工批准门

`proposal + specs + design + tasks` 完成后，必须由用户明确批准，才能开始实现。不得因 OpenSpec 能自动 apply 就跳过批准。
