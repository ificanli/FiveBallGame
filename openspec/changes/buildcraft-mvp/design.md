## Context

M2 已有确定性物理、事件流、三态、五球槽、组合评价、结算/保留/爆仓和纯数据 `CoreLoopSnapshot`。M3 增加跨桌持久状态、内容配置、受控随机、徽章事件读取、道具命令与中文表现，风险不在“能不能加倍率”，而在规则顺序、状态爆炸、奖励刷取、配置失效以及三套 Build 实际仍玩成同一种路线。

专项设计稿列出 5～7 条长期流派，但三桌 MVP 若同时铺开会导致每条都只有零散加分卡。M3 固定 18 枚徽章、三条主打法，每条 6 枚；其余污染、清台等候选暂不进入正式池，只保留未来扩展空间。

## Goals / Non-Goals

**Goals:**

- 用 18 枚可审计徽章形成三条可观察的击球策略。
- 让徽章结算读取 M1/M2 真实事件，不从动画或 UI 推断。
- 建立可复现的三桌短 Run、三选一、补球和六种容错道具。
- 默认玩家界面完整使用简体中文，同时保持规则键和回放稳定。
- 用确定性代理发现死卡、恶性组合和死亡墙，再由真人判断 Build 是否成立。

**Non-Goals:**

- 不实现完整八轮 24 桌、庄家内容库、商店经济或元进度。
- 不实现 70～90 枚徽章、全部七流派、随机补给墙或自然袋口物理。
- 不实现 Steamworks、云存档、联网、PvP、正式商业美术、手柄或大规模多语言。
- 不以机器人胜率证明好玩，不以提高目标分掩盖无条件强卡。

## Decisions

### 1. `RunSnapshot` 包含 `CoreLoopSnapshot`，但不反向污染物理/单桌规则

新增纯数据 Run 聚合，保存 Seed、随机流、桌索引、徽章、道具、奖励和统计；当前桌继续由 `CoreLoopSnapshot` 表达。Run 控制器负责跨桌命令，单桌控制器继续负责出杆和杆后状态。

这样教程仍可独立运行，M1/M2 回放无需升级成万能格式。拒绝把徽章和奖励字段塞进 `TableSnapshot`。

### 2. 徽章使用声明式条件/效果 + 少量白名单处理器

18 枚徽章配置声明 ID、中文键、流派、角色、触发阶段、条件、效果和上限。通用效果只允许 `add_base`、`add_multiplier`、`multiply_multiplier`、`grow_counter`、`modify_wall_charge` 等白名单操作；复杂条件由注册处理器读取规范事件摘要。

不采用任意脚本字符串或动态表达式执行，避免内容成为未测试代码。每个处理器必须有表驱动测试和序列化证据。

### 3. 结算上下文冻结真实物理证据

每杆停止时生成 `SettlementContext`：最佳组合、参与槽位、力度、每球激活来源/深度、有效撞库、复制/染色、保留历史、剩余杆数与防护状态。徽章只读取该冻结上下文，不能查询已经被动画或下个命令修改的场景。

预览和正式结算调用同一 `BadgeSettlementPipeline`。成长变更只在正式结算提交，预览不得偷长经验。

### 4. 三条 Build 固定为 6+6+6

- **纯净组合：**双生环、顺行仪、纯色灯、完美球组、牌型升级器、纯色顺大奖。
- **撞库连锁：**贴库客、第五档、轻推大师、连锁反应、反弹专家、多米诺。
- **功能墙冒险：**复印税、调色盘、双充能镜、墙体回路、满仓红利、贪心基金。

该列表在实现前写入版本化内容表。数值属于 TUNING，但身份与触发必须先成立。至少 13 枚直接读取/改变可操作条件；纯数值桥梁不得超过 5 枚。

### 5. 随机性拆成命名流并显式计数

Run Seed 派生 `reward`、`replenishment`、`table` 三个随机流，每次消费记录计数器。UI 展示、重开面板和预览不得推进随机。奖励候选与补球可从 `(version, seed, stream, counter, state summary)` 纯函数重建。

不使用一个全局 RNG；否则奖励动画或补球调用顺序会互相污染。

### 6. 奖励候选采用约束抽样，不暗中给最优解

开局只从三条流派启动器池各取候选；后续三选一至少一项与当前主流派有标签联动，其他项允许桥梁或转向。去重、可装备性和依赖条件先过滤，再确定性抽样。关闭界面不刷新。

槽满时选择新徽章必须替换或放弃。M3 不做出售货币，避免引入半套经济。

### 7. 道具是先验证、后提交的原子命令

道具选择过程不改规则；提交时一次验证阶段、库存、目标和参数，再返回新快照与事件。软袋/保险球槽属于“预先启用的下次风险保护”，普通编辑道具只在球静止时使用。

六球保险需要评价器支持至多六槽的临时输入，但正常持久手牌仍限制五槽；该路径单独版本化和测试。

### 8. 补球使用有限候选 + 最小修正

每桌声明投放点与未收球目标。生成器先确定性抽数字/颜色并按点位检查间距；若基础机会审计失败，只替换最少批次条目。绝不移动旧球或硬塞重叠球。全点阻塞时返回可见错误并允许清台重开。

### 9. 中文通过本地化键实现，不把中文写入规则 Hash

内部 ID、命令、阶段、牌型和事件继续英文稳定键；UI 通过 Godot Translation/项目本地化表映射简体中文。配置只引用 `name_key`/`description_key`。CI 做键覆盖和禁用原型英文词审计。

这既满足当前单语言要求，也避免未来改文案破坏回放。正式多语言切换仍不在 M3。

### 10. 机器平衡采用分层代理与成对反事实

至少三层代理：合法随机、启发式路线、Build 感知。相同 Seed 下比较无徽章和三套 Build，并保存每次决策。机器门只判定死卡、异常强弱、触发率、稳定性和死亡墙；三套录像是否可辨、玩家是否主动换路线必须真人签字。

## Risks / Trade-offs

- **[18 枚内容过多导致同质]** → 先锁三条打法和角色矩阵，逐枚做反事实；13/18 不改变决策即失败。
- **[乘算溢出或指数膨胀]** → 使用有界整数/定点规则、显式乘算顺序和上限压力测试，报告分布而非只看平均。
- **[徽章读取错误球的事件]** → 结算上下文以稳定球 ID 与事件序号冻结，副本无物理 ID 的边界沿用 M2。
- **[预览与结算不一致]** → 同一管线，预览禁止持久写入，属性测试比较两者。
- **[奖励可通过重开刷取]** → 候选保存进快照，界面生命周期不推进随机计数。
- **[补球卡死/重叠]** → 有限合法点、明确失败、清台重开恢复；不无限 while 随机尝试。
- **[道具替代核心弹射]** → 只作用于已获得球或单次风险，不直接生成完整组合；使用率与路线变化纳入真人观察。
- **[中文字体或长文案破版]** → 固定分辨率截图/适配测试 + 导出包真人检查；不靠缩小字体糊弄。
- **[云 Windows 完整回放过慢]** → 先保留本地 Windows 全量与云 Linux 全量；M3 单独优化案例分层/缓存，不降低批准的重复次数。

## Migration Plan

1. 在规划分支获批后建立 `feature/buildcraft-mvp`，记录批准 commit 和 M2 回退点。
2. 先加入本地化基础与配置审计，把现有 M2 玩家文字迁到中文但不改规则键。
3. 建立 Run/徽章/道具纯数据模型和序列化，保持 M1/M2 全回归。
4. 先实现结算上下文与 6 枚代表徽章（每流派 2 枚）验证架构，再扩到 18；不得靠复制模板凑数。
5. 实现补球、六种道具和三桌状态机，增加跨桌回放。
6. 接表现层、奖励界面、中文 HUD 与统计导出。
7. 运行配置审计、单测、Golden/Run 回放、压力、代理对照、双平台导出与独立 Gate I。
8. 最后进行真人 15～25 分钟 Run、三套录像盲辨和中文可读性验收。
9. 若三套 Build 录像相同或玩家不改球路，暂停加内容，回到徽章触发结构；不得进入 M4。

## Open Questions

- 18 枚徽章具体 TUNING 数值在实现批次中以测试和报告拟合，但不得改变上述身份与触发条件而绕过 Gate P。
- 三桌目标分/杆数先作为版本化 TUNING 配置；最终通过值必须有真人时长与代理分布证据。
