## Context

M1 已有纯数据物理快照、固定步长模拟器、稳定 ID、物理事件、墙体效果解析、轨迹预测和技术桌表现适配器。现有 `physics-table-wall-effects` 刻意把复制/染色停在技术事件层；M2 必须在不污染物理内核的前提下建立跨多杆持久规则状态。

约束：规则必须 Headless 可运行；Godot 节点不得成为真相源；M1 回放仍须兼容；同一物理 tick 内可能连续发生收集、复制、染色与爆仓；真人验收才能判断理解与可玩性。

## Goals / Non-Goals

**Goals:**

- 在物理模拟之上建立单一、确定性的规则事件消费顺序。
- 用可序列化快照表达球三态、球槽、组合、分数、杆数、墙充能和回合阶段。
- 让纯规则层可独立完成多杆教程回放、单元测试与 Hash 对照。
- 复用 M1 模拟器和预测器，不分叉第二套碰撞逻辑。
- 将教程桌 UI 限制为快照渲染与命令提交适配器。

**Non-Goals:**

- 不把组合或回合规则塞进 `PhysicsSimulator`。
- 不实现补球、袋口、清台道具、徽章、奖励、Run、存档、庄家或 PvP。
- 不在 M2 调整 M1 物理常量；若真人发现手感回归，单独记录并按物理规格处理。
- 不以自动代理通过教程代替真人理解和 15 分钟稳定性验收。

## Decisions

### 1. 使用分层 `CoreLoopSnapshot`，物理快照作为其组成部分

新增纯数据核心快照，包含 `TableSnapshot`、每个数字球的收集状态、五格 `HandSlot`、累计分、目标分、剩余杆数、回合阶段、墙体逐杆充能、爆仓锁和规则版本。所有变更返回新快照/确定性结果，不读取场景节点。

选择该方案是因为多杆状态已经超出单次 `SimulationResult`，但物理快照仍是唯一位置/速度真相。备选方案“在 BallState 上继续堆 UI/计分字段”会把跨杆产品规则耦合进物理内核，拒绝。

### 2. 物理事件先稳定排序，再由单一规则归约器消费

M1 模拟器继续产生带 tick、稳定参与者 ID 和事件序号的事件。`CoreLoopReducer` 按 `(tick, event_sequence)` 顺序消费：

1. 解析物理接触与激活传播；
2. 对首次有效接触尝试收集；
3. 解析实际撞墙球的功能墙效果；
4. 每次槽位新增后立即检查容量；
5. 爆仓后设置本杆规则锁，仅让物理继续。

这样可避免 UI 回调顺序或字典遍历顺序改变结果。备选方案“模拟结束后批量扫描碰过哪些球”无法表达先后、墙体归属和第六球发生时机，拒绝。

### 3. 球激活是单杆临时集合，收集状态是跨杆持久状态

每杆开始清空激活集合并恢复每块墙的逐杆充能。本手球若在新杆中被母球/激活球有效碰撞，可重新进入本杆激活集合并触发功能墙，但不得重复收集。废球只参与物理，不进入激活集合。

这保留“继续保留后，把已有本手球撞去加工”的设计价值，同时防止废球继续制造资源。备选方案“本手球跨杆永久激活”会让无因果的碰墙生效，拒绝。

### 4. 槽位身份使用可空 `physical_ball_id`，副本不伪造实体

物理收集槽保存非空 ID；复制槽保存空 ID、来源球 ID和来源事件 ID。染色只通过非空物理 ID 定位槽位，因此不会误改副本。槽位顺序就是收集/复制事件顺序，并作为同分择优的最后稳定键。

备选方案“给副本分配虚拟球 ID”容易被误当作桌面实体并污染染色、状态转换和回放，拒绝。

### 5. 组合评价采用枚举候选子集，而非规则优先级短路

最多五格，穷举所有非空槽位子集成本固定且极小。每个子集判断其最强类别并生成候选，再按规格中的基础分、倍率、长度和槽位索引排序选唯一最佳值。组合倍率放在带 `combo_rules_version` 的数据表中。

该方案能自然处理污染球和多重候选，测试也直观。备选方案“按五球满贯→同色顺→……找到即停”会把类别优先级错误等同于实际得分，拒绝。

### 6. 回合采用显式有限状态机

阶段至少为 `AIMING`、`SIMULATING`、`POST_SHOT_DECISION`、`WON`、`LOST`。只有状态允许的命令可以执行：

- `AIMING + shoot`：验证输入、扣一杆、重置单杆激活/充能、运行模拟；
- 模拟停止：按球槽、爆仓和剩余杆数转移；
- `POST_SHOT_DECISION + settle/keep`：原子结算或保留；
- 终态只接受 reset。

规则 API 对非法命令返回明确拒绝结果而非静默修改。备选方案“多个布尔值 is_moving/is_deciding/is_over”容易产生矛盾组合，拒绝。

### 7. 多杆规则回放与 M1 物理 Golden Replay 并存

不改写已有单杆 replay schema。新增版本化 core-loop session case，记录初始核心快照与离散命令序列；输出逐命令快照摘要、规则事件、最终 Hash。Hash 采用稳定字段顺序和量化后的物理值，忽略动画时间、粒子和本地化文本。

这样 M1 回归继续定位物理漂移，M2 回放定位规则/时序漂移。把两者强行升级成一个破坏性格式收益低、迁移风险高。

### 8. 教程桌使用固定脚本化配置，但不脚本化玩家结果

教程配置固定 Seed、布局、目标分、杆数和墙体，确保可重复验收；玩家仍自由选择角度、力度及结算/保留。界面从规则快照派生可用按钮，并复用 M1 技术桌绘制与输入。

目标分和杆数在实现批次中先以数据配置，机器测试只验证规则；真人验收前允许不改变规格的数值调优，但每次调优必须更新配置版本和验收记录。

## Risks / Trade-offs

- **[同一 tick 多接触顺序改变收球或爆仓]** → 沿用模拟器稳定事件序号，新增密集碰撞与五槽边界 Golden cases，禁止依赖容器遍历顺序。
- **[规则归约器与物理墙体解析重复应用效果]** → M1 resolver 只产出规范墙体事件；M2 reducer 是唯一修改球槽/生命周期的入口，并用事件 ID 防重复消费。
- **[组合枚举实现虽小但边界多]** → 使用表驱动案例覆盖每个类别、污染球、重复数字、并列候选和副本。
- **[爆仓发生后仍在运动，表现可能让玩家误以为还能收]** → 立即清空槽、显示爆仓锁定反馈；剩余碰撞仅做物理，规则日志明确 `ignored_after_bust`。
- **[固定教程可能无法自然触发全部验收路径]** → 提供开发/测试用固定场景与正式教程同规则层；真人清单允许通过重置和不同路线覆盖，而不是添加作弊到正式 UI。
- **[M2 UI 扩张侵占正式美术时间]** → 只要求清楚、可操作和归属反馈，正式视觉资产继续 CUT。
- **[组合倍率仍属调参]** → M2 锁定版本表建立可测试基线；未来调整必须修改能力规格或新增版本，不静默覆盖回放。

## Migration Plan

1. 在 feature 分支先添加规则数据模型和序列化，不改变现有技术桌入口。
2. 添加事件归约器、组合评价器和状态机，以 Headless 测试及 M1 全回归保护边界。
3. 新增多杆规则回放格式与案例；保留旧 replay schema 和 manifest。
4. 将现有技术桌适配为教程桌入口，并保留可独立运行的 M1 测试场景或测试构造器。
5. 通过 Windows/Linux CI、导出启动、独立 Gate I 和真人 Gate 后再替换默认主场景。
6. 若 M2 集成失败，回退教程主场景与新增规则调用；M1 模拟器、现有 specs 和 Golden cases 不迁移、不删除。
