## Context

M0 已提供 Godot 4.7.1、GdUnit4、Golden Replay 占位契约、Headless/CI 与双平台空导出。当前没有正式物理或规则实现；`src/physics/` 等目录为空。网页原型只读，可用于固定球路与真人手感对照，但其 HTML/JS 结构不迁入正式工程。

本变更横跨物理数据模型、模拟器、输入、预测、墙体事件、回放、场景适配和 CI。确定性目标是“规则结果可复现并可定位差异”，不是承诺任意 CPU/平台每个浮点位永久完全一致。

## Goals / Non-Goals

**Goals:**

- 建立不依赖 Node2D 状态的规则快照、固定步长模拟器和稳定事件顺序。
- 让正式运动、辅助预测、Golden Replay 共用同一个推进入口。
- 将物理参数集中版本化，并让每条回放显式声明版本。
- 提供可视技术桌，但保持表现层单向读取规则状态。
- 在开始组合与 Run 之前暴露穿透、能量爆炸、低速拖尾和跨平台漂移。

**Non-Goals:**

- 不追求真实台球旋转、塞球、摩擦各向异性、球袋或传统犯规。
- 不实现组合、球槽、计分、结算/保留、爆仓、补球或废球三态。
- 不引入 Steam、网络同步、存档、内容编辑器或正式美术。
- 不以自动测试代替作者对击球手感的真人判断。

## Decisions

### 1. 纯数据快照是唯一规则真相

使用可序列化的数据对象表达球、墙、桌面、出杆输入、模拟配置和结果。Godot 场景节点只持有规则 ID，并在每个模拟 tick 或插值帧读取快照更新表现。

原因：Headless、预测、回放和未来 PvP 都必须在没有场景树副作用的情况下运行同一规则。

备选：直接使用 CharacterBody2D/RigidBody2D。否决，因为预测复用、事件排序与跨平台回放难以控制，且节点状态会污染规则边界。

### 2. 固定步长 + 有界动态子步

基础 tick 初值采用 `1/120s`。每个 tick 根据最大位移与球直径计算确定性的子步数量，并设置硬上限；最大力度下单子步位移不得跨过关键碰撞尺度。所有参数集中在版本化 `PhysicsConfig` 中。

原因：仅固定 tick 仍可能在高速下穿透；完全连续碰撞检测的复杂度超出 M1。受控子步是首个纵切的可测试折中。

回退：若最大允许子步仍无法消除穿透或性能不可接受，暂停内容开发，针对圆—圆/圆—线段引入 time-of-impact 求解，并更新物理版本与 Golden。

### 3. 碰撞解析采用稳定键排序

每个子步先收集候选接触，再按稳定键排序，例如：`接触时间桶 → 事件类型优先级 → min(entity_id) → max(entity_id) → wall_id`。同一接触使用固定迭代次数解析，禁止依赖 Dictionary 遍历顺序。

原因：多球同时接触没有唯一物理解；项目更需要可重复、可调试的约定。

备选：按场景节点顺序或发现顺序解析。否决，因为导入、平台和容器顺序可能改变结果。

### 4. 双精度运行，规范化序列化与 Hash

GDScript `float` 用于运行；对规则输出进行显式字段排序、非有限数检查和固定小数网格量化后再序列化/Hash。量化只用于比较与静止快照，不在每个积分步骤粗暴截断运动。

原因：逐 tick 量化会显著改变手感；完全比较原始浮点位又会制造无意义的平台噪声。规范化层只允许吞掉不改变碰撞顺序、墙体归属和停止结果的微小差异。

任何导致事件顺序、触发对象、球体最终离散位置桶或停止 tick 改变的差异仍必须失败。

### 5. 统一模拟入口，预测以克隆快照运行

`simulate(snapshot, shot_input, mode)` 是唯一推进边界。正式运动运行到停止；预测从同一快照克隆并运行到辅助模式预算或事件预算，然后把事件转换为可视路径。不得在 UI 中另写射线碰撞公式。

原因：这是保证首碰和墙体归属一致的最直接方式。

性能策略：瞄准输入变化时取消旧预测；对相同快照 revision、方向、力度和模式缓存结果；预测预算有硬上限。

### 6. 物理事件与墙体规则分层

物理层只产出球—球、球—墙接触事件和运动状态。最小规则解析器根据有序接触维护本杆激活图，并产生复制/染色事件。染色改变球的规则颜色字段，但不改变质量、半径或碰撞响应；复制只产生技术结果记录，不生成物理球。

原因：功能墙需要物理因果，却不应把组合和球槽提前塞进物理求解器。

事件同 tick 顺序固定为：解析物理接触 → 更新激活因果 → 应用实际撞墙球的墙体效果 → 记录规范化事件。每面复制墙每杆基础充能 1 次，在新杆开始重置。

### 7. ID 与随机数显式稳定

初始快照按稳定顺序分配整数球 ID 和墙 ID。所有 Seed 随机生成通过单一、显式初始化的 RNG 完成；生成后快照必须完整保存，回放不得重新依赖随机调用顺序。

原因：回放应以快照为最终输入，Seed 用于来源追踪和重建验证，而不是隐藏依赖。

### 8. Golden Replay 分为输入、实际输出、预期摘要

案例 JSON 保存 schema/physics/content 版本、Seed、初始快照、ShotInput 和预期摘要。运行器输出完整结构化结果；比较器报告首个事件差异和首个状态字段差异。Golden 更新必须显式执行，普通测试不得自动覆盖预期文件。

案例类别由 manifest 审计，M1 Gate 要求 15～20 条并覆盖规格列出的风险类。

### 9. 技术桌与网页对照

Godot 技术桌使用简单几何和调试可视化：球 ID/数字/颜色、速度、接触点、激活来源、墙体充能、预测路径、tick 和 Seed。网页原型选择 5～10 个可手工复现的球路，记录力度档、方向、首碰、主要停球节奏与作者主观评价。

网页与 Godot 不要求逐像素或逐坐标相同；对照目标是控制可靠性、反弹直觉、停止节奏和漂亮连锁的可学习性。最终“手感不低于网页原型”由真人 Gate 判定。

### 10. CI 分层

- 快速单元层：数学、输入校验、序列化、Hash、单碰撞、墙体归属。
- Golden 层：案例与 100 次重复运行。
- 跨平台层：Windows/Linux 生成规范化 JSON，比较并上传差异 Artifact。
- 真实启动层：技术桌 Headless 启动；可视检查由本地启动和截图/真人操作完成。

CI 失败不得自动更新 Golden。

## Risks / Trade-offs

- [多球同时接触对解析顺序敏感] → 固定接触排序与迭代次数，并为密集案例保存首个差异。
- [子步上限在极端布局仍可能穿透] → 最大力度压力案例；失败则停止并升级到 time-of-impact，而不是继续堆内容。
- [规范化容差掩盖真实漂移] → 事件身份/顺序、触发归属和停止 tick 不使用宽松容差；只规范化连续数值字段。
- [预测计算影响瞄准响应] → 取消过时任务、缓存、预算分档；完整模式允许更高成本但不得阻塞输入。
- [调参导致 Golden 大面积变化] → 所有行为参数属于 `physics_version`；有意变化必须审查差异并升级版本。
- [GDScript 性能不足] → 先用 7 球、有限预测预算测量；只有证据表明不足时才评估 GDExtension/C#，本 Change 不预装。
- [网页手感无法数值等价迁移] → 将机器对照和真人主观对照分开记录，不伪造精确等价结论。

## Migration Plan

1. 在 feature 分支实现纯数据与测试，不替换任何既有玩法（当前无正式玩法可迁移）。
2. 先让失败单元测试和最小 Golden 案例落地，再逐层接入碰撞、停止、墙体和预测。
3. 技术桌达到机器门后进行本地真实启动和网页对照。
4. 若 Gate I 或真人手感门失败，保留 M0 main 基线，回退该 feature 分支；不归档 Change、不进入 M2。
5. 通过后归档 Change，冻结 `physics_version=1` 的规格与 Golden 基线。

## Open Questions

- 五档速度的最终绝对值、恢复系数、摩擦系数、停止阈值与收尾时长均为 TUNING；在不改变五档离散、确定性和验收行为的前提下由网页对照与真人调参确定。
- 完整辅助模式的最终事件预算可根据性能测量调整，但必须比标准模式更长且不得变成自动解题。
